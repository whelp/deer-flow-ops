# 根因假设树

## 使用方式

按下面五类依次过一遍，生成 2–4 个假设。
**排序原则：先排除人为变更 → 再看容量 → 再看协议配置 → 最后才到硬件。**

统计上，人为变更和容量问题是主要来源；硬件故障虽然"听起来更专业"，但概率排后面。
值班时先排除常见原因，比先怀疑硬件更省时间。

---

## 五类假设

### 类 1 · 变更类（优先级最高）

- **典型证据**：告警时刻与变更窗口重合；告警范围与变更范围重叠
- **验证动作**：拉取变更单列表，比对时间与对象；查配置差异（变更前后 diff）
- **预期结果**：变更对象集合 ⊇ 告警对象集合，且时间差 < 30 分钟
- **反证**：发生过变更的对象没有告警，或告警对象不在变更范围内

### 类 2 · 容量类

- **典型证据**：会话数 / 连接数 / 带宽 / 表项数接近规格上限；高峰时段规律性出现
- **验证动作**：取故障时刻与前一周期同时刻的容量指标做对比
- **预期结果**：故障时刻指标显著高于基线，或已接近规格阈值
- **反证**：容量指标平稳，无爬升趋势

### 类 3 · 硬件 / 链路类

- **典型证据**：光功率异常、误码增长、CRC 错误、单端口反复 flap、单设备指标突变
- **验证动作**：查光功率历史曲线、误码计数增量、端口 flap 计数
- **预期结果**：单点指标单调劣化，且劣化开始时间早于其他告警
- **反证**：同类端口普遍异常（那就是共因，不是单点硬件）

### 类 4 · 协议 / 配置类

- **典型证据**：STP 拓扑变更激增、路由邻居震荡、BPDU / 认证报文异常
- **验证动作**：查拓扑变更计数、邻居状态历史、协议报文统计
- **预期结果**：协议震荡计数与告警时刻同步上升
- **反证**：协议层指标无异常

### 类 5 · 外部 / 上游类

- **典型证据**：多台本地设备同时不可达；上游运营商侧或云端变更通知
- **验证动作**：查上游链路状态、运营商公告、跨机房对比
- **预期结果**：上游侧存在问题，本地设备本身指标正常
- **反证**：只有本地单点异常，其他分支正常

## 每个假设的必备五要素

写成表格，缺一项就不完整：

| 项 | 要求 |
|---|---|
| 假设 | 一句话，可判定真假 |
| 支持证据 | 引用输入中的**具体条目**，不写"从告警看" |
| 不成立的条件 | 什么现象出现就说明这个假设错了 |
| 验证动作 | 一条可执行的查询 / 命令 |
| 预期结果 | 假设成立时，验证后应看到什么 |

---

## 常见陷阱

- **把"最严重的告警"当根因** —— 严重级别反映影响面，不反映因果位置
- **把"最晚出现的告警"当根因** —— 恰恰相反，根因通常最早
- **把"我熟悉的领域"当根因** —— 网络工程师容易把一切归为网络问题
- **只给一个假设** —— 那叫猜。至少两个，最好三个
- **验证动作写成"进一步排查"** —— 这不是动作，是拖延
