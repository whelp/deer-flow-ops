# 告警收敛规则

## 为什么必须收敛

监控系统的设计目标是"不漏报"，不是"不重复报"。
所以一次真实故障会被多个采集点、多个层级、多个维度重复捕捉，
最终以几十条告警的形式涌到值班台。

**收敛的目的不是减少数量，是找出"几个独立事件"。**

40 条告警可能只是 1 个事件，也可能是 4 个互不相关的事件。
这两种情况下的处置优先级完全不同。

---

## 四种归并规则

### 1. 同源合并

同一个对象上的同类告警，在时间窗内合并为一条"事件"。

- 判据：`对象 + 告警类型 + 时间窗`
- 例：同一台交换机的同一端口 30 分钟内 flap 27 次 → **1 个事件**，不是 27 条

### 2. 同窗合并

时间上高度聚集（通常 < 2 分钟）的告警，即使对象不同，也要放在一起看。

- 判据：`时间差 < 2 分钟`
- ⚠️ **注意**：同窗 ≠ 同因。时间接近只是提示你去查关联，**不构成因果**。

### 3. 同域合并

落在同一管理域、同一机房、同一电源、同一上行链路上的告警归为一组。

- 判据：`共享基础设施`
- 这一条最需要拓扑信息。没有拓扑就标 `待确认`，不要猜。

### 4. 主从合并（最重要）

识别**根告警**和**衍生告警**，只保留根告警，衍生告警降级为证据。

- 判据：告警 B 的出现需要以告警 A 为前提
- 例：链路 down 会导致路由收敛、业务超时、会话中断 ——
  **链路 down 是根告警，后三者是衍生告警**

## 常见告警瀑布形态

这些模式值得背下来，命中率很高。

| 根因 | 典型瀑布链 |
|---|---|
| 光模块老化 / 尾纤劣化 | 收光功率下降 → 误码增加 → 链路 flap → STP 拓扑变更 → 广播泛洪 → 上层 CPU 飙升 → 业务时延上升 |
| 端口 flap | 端口 up/down 反复 → STP TC BPDU 激增 → 全 VLAN 泛洪 → 核心 CPU / 广播报文速率告警 |
| 上游设备重启 | 设备离线 → 下挂设备批量不可达 → 路由邻居震荡 → 业务中断面扩大 |
| 电源 / 风扇故障 | 温度上升 → 芯片降频 → 丢包 → 时延抖动 |
| 容量打满 | 会话数 / 连接数接近规格 → 新建失败 → 业务报错 → 应用侧重试风暴 |
| 变更失误 | 变更完成时刻起 → 特定业务域集中告警 → 与变更范围高度重合 |
| 时钟 / 认证 | NTP 失步 → 证书校验失败 → 批量组件失联 |

**判断技巧**：看谁在时间线上更早，看谁在拓扑上更靠上游。
两个都指向同一条告警 → 它就是根告警。

## 收敛输出格式

```
事件组  涉及对象                首条时刻   告警条数   角色
E1      acc-sw-31 GE1/0/24      02:11      27         根因候选
E2      agg-sw-11, core-sw-01   02:14      8          衍生（源于 E1）
E3      fw-edge-01              02:20      1          待观察
```

条数最多的通常是症状组；**时间最早 + 位于拓扑上游的，才是根因候选。**
